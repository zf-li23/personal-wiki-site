[Programming Fundamentals](/4.1) is concerned with "how to compute": decomposing a problem into steps and writing an algorithm with variables, branches, loops and functions. Once programs grow large, the difficulty gradually shifts from algorithms to organization: hundreds or thousands of functions share a pile of data, and a change anywhere may ripple through the whole program. **Object-oriented programming** is concerned with "how to see": it first abstracts the things in the problem domain into **objects**, lets each object maintain its own data and provide services, and then lets the objects cooperate to accomplish the task. This course discusses this way of organizing programs, mainly in C++ and with Python for comparison: its core ideas of **abstraction** and **encapsulation**, the language mechanisms that implement them, and how to use these mechanisms to design programs that are easy to modify and extend. The last chapter discusses the other half of the reality of programming today: a large share of code is generated, modified and reviewed by AI.

The main thread of the chapters runs from a single class to relations between classes, and then to mature design. The course first compares the procedural and object-oriented **programming paradigms**, and explains how a C++ program made of several files becomes an executable through compilation, linking and building. Next come the basic mechanisms of classes and objects: a **class** separates interface from implementation by access control; constructors and destructors make initialization and cleanup of objects happen automatically, which gives the central idiom of C++ resource management, **RAII**; operator overloading lets user-defined types be used like built-in types; and references, copying and moving determine how the ownership of a resource is passed between objects. The course then discusses relations between classes and generality: composition and **inheritance** are two ways of reuse, and **virtual functions** select at run time which implementation is called, which realizes **polymorphism**; **templates** provide another kind of polymorphism, resolved at compile time, namely **generic programming**. The standard library built on templates (containers, iterators and algorithms; strings, streams and regular expressions; function objects, lambdas and smart pointers) shows how these mechanisms are used in large-scale code. The chapter on **design patterns** uses a running example to show how to combine these mechanisms to cope with changing requirements, and distills design principles such as the open-closed principle from it. The last chapter uses the framework "**coding agent** = model + **agent harness**" to discuss the models, tools, workflows and risks of AI-assisted programming.

This course builds on [Programming Fundamentals](/4.1): the **structures** there are the forerunners of classes, and the **pointers** and dynamic memory there are managed here by RAII and smart pointers. How the data structures behind the standard library containers are implemented and where their complexity comes from is the subject of [Data Structures and Algorithms](/4.3); the formal theory of regular expressions is found in [Formal Languages and Automata](/4.8); and larger questions of software design, such as requirements, architecture, testing and version control, are treated in [Software Engineering](/4.14). The Python comparisons in this course also lay the groundwork for the object model of libraries such as NumPy and pandas in [Scientific Computing with Python](/4.4).

In programming fundamentals I came to feel that programming is using a language the machine can understand to represent the world. The next question is: what way of representing it makes it easy for people to understand? In the stage of "old-school programming" (writing code line by line without the help of AI), the most natural way for a person to think is probably procedural: do this first, then that. In complex engineering practice, however, another mode of thinking is needed. I believe object-oriented programming should be understood as the study of how the world is composed: what things there are, what each of them knows and can do, and how they are related to one another. Many terms of this discipline convey deep information in their very wording: "object", "class", "inheritance", "encapsulation" and "interface" can all be linked directly to real life. In the age of AI-assisted programming, the object-oriented view seems even more natural: the details of syntax can be left to AI, while what people are responsible for is precisely splitting the problem domain into objects, specifying their responsibilities and interfaces, and then checking whether the implementation written by AI conforms to that design.

In the old-school stage, though, the syntactic details of this course did give me headaches: when constructors and destructors run, the rules of copying and moving, and the error messages of templates often cost more effort than the object-oriented ideas themselves. C++ builds direct language support for object orientation on top of C while retaining control over memory and performance, which is exactly why it is complicated. Python carries "everything is an object" through to the end: integers, functions and classes themselves are all objects, and together with **duck typing** many designs that need special mechanisms in C++ are much lighter to write. This course therefore gives Python code alongside C++, so that by comparing the two it is easier to see which parts are object-oriented ideas and which are mechanisms specific to C++.
