The previous chapter discussed the general questions in the design of an **instruction set**; this chapter presents one concrete instruction set in full: **RISC-V**. It is the instruction set used in the labs of this course, and it is the basis for understanding the processor designs of the following chapters: the single-cycle processor of [4.10.6](/4.10.6) and the pipelines of later chapters aim at implementing a subset of it. We first introduce the modular structure and the **registers** of RISC-V, and then teach the base integer instructions class by class (RV32I, with the 64-bit RV64I and the multiply/divide extension where necessary), using C programs and the assembly code generated by GCC to show how the constructs of high-level languages map onto instructions. Next come the function-calling convention and the stack frame, which is the machine-level implementation of the **call stack** of [4.1.4](/4.1.4); finally we show how instructions are encoded into 32-bit machine code. All assembly code in this chapter has been compiled with RISC-V GCC; the semantics of the instructions follow the current specifications published by RISC-V International.

## 3.1. Overview of RISC-V

### 3.1.1. History and Characteristics

**Definition 3.1.1 (RISC-V)** The open RISC instruction set architecture whose design began in 2010 at the University of California, Berkeley, and which is now maintained by the nonprofit RISC-V International, is called **RISC-V** (pronounced "risk-five").

The V in the name indicates that this is Berkeley's fifth generation of RISC designs, counting from RISC I in 1980. It was started by Krste Asanović, David Patterson, Andrew Waterman, Yunsup Lee and others, originally for teaching and research: existing instruction sets were either restricted by patents and licenses or burdened by decades of historical baggage. RISC-V has several outstanding characteristics:

- Open: the specification is released under open licenses, and anyone may implement, modify and sell RISC-V processors for free, without license fees. The standard is developed through public processes by RISC-V International (named the RISC-V Foundation when founded in 2015, moved to Switzerland and renamed in 2020).
- Simple: it learns from earlier generations of RISC and omits designs, such as branch delay slots and condition codes, that hamper later implementation techniques. The base integer **instruction set** RV32I has only 40 instructions, and its specification takes only a dozen or so pages; by comparison the x86 manual has more than five thousand pages.
- Modular: a small, fixed base instruction set plus optional standard extensions, so that anything from a microcontroller of a few thousand gates to a supercomputer can implement just the parts it needs (Section 3.1.2).
- Stable: the ratified parts are frozen and will not change, so software written on them can run for a long time.

### 3.1.2. The Base Instruction Sets and Extensions

Every RISC-V implementation consists of one base integer instruction set plus some extensions, denoted by letters or names.

| Base instruction set | Description |
|---|---|
| RV32I | 32-bit integer instruction set, 32 general-purpose registers of 32 bits |
| RV64I | 64-bit integer instruction set, 64-bit registers, adding 64-bit memory access and 32-bit "word" arithmetic instructions |
| RV32E, RV64E | Embedded versions with only 16 general-purpose registers |
| RV128I | 128-bit version, not yet frozen |

The register width is denoted XLEN: XLEN = 32 in RV32 and XLEN = 64 in RV64. The commonly used standard extensions:

| Extension | Content |
|---|---|
| M | Integer multiplication and division |
| A | Atomic operations: load-reserved / store-conditional and atomic read-modify-write, for multiprocessor synchronization ([4.11.6](/4.11.6)) |
| F, D, Q | Floating point in **single precision**, **double precision** and quad precision, conforming to **IEEE 754** ([4.10.4](/4.10.4)), with an additional 32 floating-point registers `f0`–`f31` |
| C | Compressed instructions: 16-bit encodings of common instructions, which shrink code by about 25%–30% (Section 3.8.8) |
| Zicsr, Zifencei | Control and status register access instructions, and the instruction-fetch fence; originally part of I and split off in 2019 |
| B | Bit manipulation (Zba address computation, Zbb basic bit manipulation, Zbs single-bit operations), such as rotates and leading-zero count |
| V | Vector extension: the vector length is determined by the hardware, so the same program can run on hardware with different vector lengths |
| H | Hypervisor (virtualization) support ([4.11.9](/4.11.9)) |

IMAFD together with Zicsr and Zifencei is called G (general), so `RV64GC` is `RV64IMAFDC_Zicsr_Zifencei`, a common configuration for 64-bit processors that run Linux. GCC specifies the target with spellings such as `-march=rv32im` and `-march=rv64gc`. To avoid software fragmentation caused by arbitrary combinations of extensions, RISC-V International also defines profiles: for example, RVA23 for application processors (ratified in 2024) prescribes the set of extensions that must be supported to run a general-purpose operating system, including the vector extension V and the hypervisor extension H. Some letters in early plans (such as L for decimal floating point and N for user-level interrupts) have been abandoned, and the packed-SIMD extension P has not been ratified.

The ThinPAD processor in the labs of this course is required to implement only a subset of RV32I: the 19 instructions needed to run the basic version of the monitor program are `add`, `addi`, `and`, `andi`, `auipc`, `beq`, `bne`, `jal`, `jalr`, `lb`, `lui`, `lw`, `or`, `ori`, `sb`, `slli`, `srli`, `sw`, `xor`; the version supporting interrupts and exceptions adds `csrrc`, `csrrs`, `csrrw`, `ebreak`, `ecall`, `mret`, and the version supporting virtual addresses adds `sfence.vma`.

### 3.1.3. Privilege Modes and Control and Status Registers

The RISC-V specification has two volumes: the unprivileged ISA defines the instructions available to ordinary programs, and the privileged architecture defines the mechanisms needed by operating systems and firmware. The privileged architecture defines three privilege modes:

| Mode | Use | Required |
|---|---|---|
| M (machine) | Highest privilege; firmware and simple embedded systems | Yes |
| S (supervisor) | Operating-system kernel, supports virtual memory | Optional |
| U (user) | Applications | Optional |

A simple microcontroller implements only M mode; a processor that runs Linux implements M, S and U modes. The state and configuration of the processor are kept in control and status registers (CSRs), which have a separate 12-bit address space and are read and written with the `csrrw`, `csrrs`, `csrrc` and other instructions of the Zicsr extension. For example, `mtvec` holds the entry of the exception handler, `mepc` saves the address of the instruction that caused the exception, and `mcause` records the cause; the two **counters** `cycle` and `instret` count the number of **clock cycles** and the number of completed instructions, respectively, and user programs read them with the pseudoinstructions `rdcycle` and `rdinstret`; their ratio is the **CPI** a program actually achieves ([4.10.1](/4.10.1#sec-1.4.2)). The `ecall` instruction traps from U mode to a more privileged mode and is used for system calls ([4.11.1](/4.11.1)). Exceptions, interrupts and privilege modes are discussed in detail in later chapters.

## 3.2. Registers and Assembly Language

### 3.2.1. The Register File

The operands of arithmetic instructions can come only from registers (load-store type, [4.10.2](/4.10.2#sec-2.1.3)), so the number and use of registers are central to an instruction set.

**Definition 3.2.1 (Register File)** The storage component of a processor that consists of several general-purpose registers and is read and written by number is called the **register file**. The register file of RV32I has 32 general-purpose 32-bit registers `x0`–`x31` (64-bit in RV64I), of which `x0` is always 0: reading it always gives 0, and writing it has no effect.

The **program counter** `pc` is not in the register file and cannot be read or written directly by ordinary instructions. The hardware implementation of a register file usually has two read ports and one write port, which exactly fits the **instruction format** with "two source registers and one destination register" ([4.10.6](/4.10.6)). Why 32? The more registers there are, the more variables the **compiler** can keep in registers; but the larger the register file, the slower the read, and the numbers take more instruction bits (32 registers need 5 bits, and three register fields take 15 bits in all), a compromise of "smaller is faster". Because `x0` is always 0, many operations need no dedicated instruction: `add x1, x2, x0` is a register move and `addi x1, x0, 5` loads a constant.

The hardware treats `x1`–`x31` alike, and their uses are fixed by software convention: each register has an **ABI** name, which is usually used in assembly programs.

| Register | ABI name | Use | Saved by |
|---|---|---|---|
| `x0` | `zero` | Constant 0 | — |
| `x1` | `ra` | Return address | Caller |
| `x2` | `sp` | Stack pointer | Callee |
| `x3` | `gp` | Global pointer | — (not allocated) |
| `x4` | `tp` | Thread pointer | — (not allocated) |
| `x5` | `t0` | Temporary; alternate link register | Caller |
| `x6`–`x7` | `t1`–`t2` | Temporaries | Caller |
| `x8` | `s0` / `fp` | Saved register; frame pointer | Callee |
| `x9` | `s1` | Saved register | Callee |
| `x10`–`x11` | `a0`–`a1` | Function arguments, return values | Caller |
| `x12`–`x17` | `a2`–`a7` | Function arguments | Caller |
| `x18`–`x27` | `s2`–`s11` | Saved registers | Callee |
| `x28`–`x31` | `t3`–`t6` | Temporaries | Caller |

With the F or D extension there are another 32 floating-point registers, with ABI names `ft0`–`ft11` (temporaries, caller-saved), `fs0`–`fs11` (callee-saved) and `fa0`–`fa7` (arguments and return values). The meaning of the "Saved by" column is explained in Section 3.7.2.

### 3.2.2. The Format of Assembly Programs

The arithmetic instructions of RISC-V are all written in the form "one operation, three operands":

```asm
op   rd, rs1, rs2      # rd = rs1 op rs2
opi  rd, rs1, imm      # immediate form: the second source is a constant
```

`rd` is the destination register, `rs1` and `rs2` are source registers, and what follows `#` is a comment. Besides instructions, an assembly source file has labels (followed by a colon, representing the address of where they are) and assembler directives that begin with a dot, which produce no instructions but tell the assembler how to organize its output: `.text` and `.data` select the code or data section, `.globl` declares a global symbol, `.word`, `.byte` and `.string` place data, and `.align` aligns.

For example, for the C statement `a = (b + c) - (d + e);`, with `a`–`e` in `s0`–`s4` in order:

```asm
add  t0, s1, s2        # t0 = b + c
add  t1, s3, s4        # t1 = d + e
sub  s0, t0, t1        # a = (b + c) - (d + e)
```

A complex expression is broken into a series of instructions with two source operands each, with intermediate results kept in temporary registers. The assembly code below generally uses ABI names; when explaining encodings we write `x` numbers.

## 3.3. Integer Arithmetic Instructions

### 3.3.1. Addition and Subtraction

| Instruction | Meaning | Note |
|---|---|---|
| `add rd, rs1, rs2` | `rd = rs1 + rs2` | |
| `sub rd, rs1, rs2` | `rd = rs1 - rs2` | |
| `addi rd, rs1, imm` | `rd = rs1 + imm` | `imm` is a 12-bit signed number in $[-2048, 2047]$, sign-extended to XLEN bits |
| `lui rd, imm` | `rd = imm << 12` | Loads a 20-bit upper immediate (Section 3.6.2) |
| `auipc rd, imm` | `rd = pc + (imm << 12)` | For **PC**-relative address computation |

There is no `subi`: subtracting a constant is adding its negative, `addi t0, t0, -1`.

Addition and subtraction in RISC-V do not detect **overflow** and there are no condition codes: the result keeps only the low XLEN bits and is written to the destination register (that is, arithmetic modulo $2^{\mathrm{XLEN}}$ in **two's complement**, [4.10.4](/4.10.4)). This matches the semantics of unsigned integers in C; signed overflow is **undefined behavior** in C, and the compiler does not check it either. When detection is needed, one or two extra branch instructions do it:

```asm
# unsigned overflow of t0 = t1 + t2: the sum is smaller than an operand
add  t0, t1, t2
bltu t0, t1, overflow

# signed overflow in general: (t2 < 0) must equal (t0 < t1)
add  t0, t1, t2
slti t3, t2, 0
slt  t4, t0, t1
bne  t3, t4, overflow
```

The second fragment rests on this: without overflow, $t_0 = t_1 + t_2$, so $t_0 < t_1 \iff t_2 < 0$; when overflow occurs this equivalence is exactly broken. If the sign of `t2` is known (for example when adding a positive immediate), one `blt` suffices.

In RV64I the registers are 64 bits, while C's `int` is still 32 bits. RV64I therefore adds the "word" operations `addw`, `subw`, `addiw` and so on: they operate only on the low 32 bits and write the 32-bit result, sign-extended to 64 bits. For example, in RV64 `*p += 5` for an `int` compiles to the three instructions `lw`, `addiw` and `sw`.

### 3.3.2. Logic and Shifts

| Instruction | Meaning |
|---|---|
| `and`, `or`, `xor rd, rs1, rs2` | Bitwise AND, OR, **exclusive OR** |
| `andi`, `ori`, `xori rd, rs1, imm` | Bitwise operation with the sign-extended 12-bit immediate |
| `sll rd, rs1, rs2` | Logical left shift, filling the low bits with 0 |
| `srl rd, rs1, rs2` | Logical right shift, filling the high bits with 0 |
| `sra rd, rs1, rs2` | Arithmetic right shift, filling the high bits with the sign bit |
| `slli`, `srli`, `srai rd, rs1, shamt` | The shift amount is an immediate |

The shift amount takes only the low 5 bits of `rs2` (6 bits in RV64), and the immediate `shamt` ranges over 0–31 (0–63 in RV64). There is no bitwise NOT instruction: `xori rd, rs, -1` (XOR with all ones) is the complement. `andi` is often used to extract certain bits (a **mask**), such as `andi t0, t0, 0xFF` to take the lowest byte. A left shift by $k$ bits is equivalent to multiplication by $2^k$, and the compiler uses it to compute the address of an **array** element (`slli t0, a1, 2` is `i * 4`); an arithmetic right shift by $k$ bits is equivalent to division by $2^k$ rounding toward negative infinity, which differs for negative numbers from the rounding toward zero of integer division in C, so for signed `x / 4` the compiler adds a correction.

### 3.3.3. Comparison

| Instruction | Meaning |
|---|---|
| `slt rd, rs1, rs2` | If `rs1 < rs2` (signed comparison) then `rd = 1`, otherwise `rd = 0` |
| `sltu rd, rs1, rs2` | Same, unsigned comparison |
| `slti`, `sltiu rd, rs1, imm` | Compare with an immediate; in `sltiu` the immediate is first sign-extended and then compared as an unsigned number |

Comparing the same bit string as signed and as unsigned numbers can give different results:

```asm
addi  t0, zero, -1     # t0 = 0xFFFFFFFF
slti  t1, t0, 1        # t1 = 1: as signed, -1 < 1
sltiu t2, t0, 1        # t2 = 0: as unsigned, 2^32 - 1 > 1
```

The distinction between signed and unsigned appears in RISC-V in three places: comparison (`slt` / `sltu`), conditional branches (`blt` / `bltu`, Section 3.5.1) and the extension mode of loads (`lb` / `lbu`, Section 3.4.3). Addition, subtraction, logic operations and left shifts are identical for both, which is a benefit of the **two's complement** representation. `sltiu rd, rs, 1` gives 1 when `rs == 0`, so testing for "equal to zero" needs no dedicated instruction either (the pseudoinstruction `seqz`).

### 3.3.4. The Multiply and Divide Extension

The product of two XLEN-bit numbers has $2 \times \mathrm{XLEN}$ bits, and the M extension has separate instructions for the low half and the high half:

| Instruction | Meaning |
|---|---|
| `mul rd, rs1, rs2` | Low XLEN bits of the product (the same for signed and unsigned) |
| `mulh rd, rs1, rs2` | High XLEN bits of the product, both operands signed |
| `mulhu rd, rs1, rs2` | High XLEN bits, both operands unsigned |
| `mulhsu rd, rs1, rs2` | High XLEN bits, `rs1` signed and `rs2` unsigned |
| `div`, `divu rd, rs1, rs2` | Quotient, signed / unsigned, rounding toward zero |
| `rem`, `remu rd, rs1, rs2` | Remainder, with the sign of the dividend |

When the full product is needed, the specification recommends writing `mulh[[s]u] rdh, rs1, rs2` immediately followed by `mul rdl, rs1, rs2` (with the source registers in the same order and `rdh` different from both `rs1` and `rs2`); likewise, when both quotient and remainder are needed, write `div` immediately followed by `rem`. The **microarchitecture** can then fuse the two instructions into a single operation. RV64 also has 32-bit versions such as `mulw`, `divw` and `remw`.

Division has two special cases. RISC-V does not raise exceptions for them (which simplifies the pipeline) but specifies definite results, and software checks with a branch when needed:

| Case | Dividend $x$ | Divisor | `divu` | `remu` | `div` | `rem` |
|---|---|---|---|---|---|---|
| Division by zero | $x$ | 0 | $2^{\mathrm{XLEN}} - 1$ (all ones) | $x$ | $-1$ | $x$ |
| Signed overflow | $-2^{\mathrm{XLEN}-1}$ | $-1$ | — | — | $-2^{\mathrm{XLEN}-1}$ | 0 |

`rem` follows the semantics of C: the quotient is rounded toward zero and the remainder has the sign of the dividend, as in `-7 / 2 = -3` and `-7 % 2 = -1`; for negative numbers it differs from the mathematical modulo operation with values in $[0, b)$. The algorithms and hardware of multipliers and dividers are in [4.10.5](/4.10.5).

## 3.4. Memory Access Instructions

### 3.4.1. Byte Addressing and Data Alignment

Memory can be viewed as a one-dimensional array of bytes with addresses starting at 0, each **byte** having its own address (byte addressing). RISC-V defines a halfword as 16 bits, a word as 32 bits and a doubleword as 64 bits, and the address of a multibyte datum is the address of its lowest byte. Adjacent word addresses differ by 4, and for `int a[]` in C the address of `a[i]` is `a + 4*i`: a C compiler multiplies by the element size automatically according to the type, whereas in assembly the programmer must compute it.

**Definition 3.4.1 (Data Alignment)** A datum of size $n$ bytes ($n$ a power of 2) stored at an address that is a multiple of $n$ is said to be aligned, and this requirement is called **data alignment**; otherwise the datum is called misaligned.

For example, the lowest two bits of the address of an aligned word are 0. Aligned data always lie within one memory word (and one cache line and one page) and can be accessed in a single access; misaligned data may straddle two memory words and need two accesses and then a merge. The base instruction set of RISC-V allows misaligned accesses, but they may be very slow, or be implemented as exceptions and emulated in software, as decided by the execution environment; x86 allows misaligned accesses, again at the cost of speed. Compilers therefore always align variables according to their types, and padding bytes may be inserted between members of a structure ([4.1.9](/4.1.9)). Instructions themselves must also be aligned: instruction addresses are multiples of 4 without the C extension and multiples of 2 with it.

### 3.4.2. Byte Order

In what order are multibyte data stored in memory?

**Definition 3.4.2 (Big-Endian and Little-Endian)** The storage scheme in which the most significant byte of a multibyte datum is stored at the lowest address is called **big-endian**; the scheme in which the least significant byte is stored at the lowest address is called **little-endian**. The order in which the bytes of data are arranged in memory is collectively called **endianness**.

For example, store the 32-bit number `0x00000180` at addresses 0–3:

| Address | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| Big-endian | `00` | `00` | `01` | `80` |
| Little-endian | `80` | `01` | `00` | `00` |

RISC-V is little-endian (the privileged specification allows an implementation to switch data accesses to big-endian, but instructions are always stored little-endian), and so are x86 and the vast majority of ARM systems; multibyte fields in network protocols are transmitted big-endian, called network byte order. As long as data are always read and written in units of the same size, endianness is invisible to the program; it must be considered when accessing an integer byte by byte, transmitting data over a network, and reading or writing binary files ([4.1.9](/4.1.9)).

### 3.4.3. Load and Store Instructions

RISC-V has only two classes of instructions that access memory, load and store, both using **base addressing** ([4.10.2](/4.10.2#sec-2.3.2)): the address is the base register `rs1` plus a sign-extended 12-bit displacement, written `offset(rs1)`.

| Instruction | Meaning |
|---|---|
| `lw rd, off(rs1)` | Read a 32-bit word (sign-extended to 64 bits in RV64) |
| `lh`, `lhu rd, off(rs1)` | Read a 16-bit halfword, sign-extended / zero-extended |
| `lb`, `lbu rd, off(rs1)` | Read an 8-bit byte, sign-extended / zero-extended |
| `sw rs2, off(rs1)` | Write the low 32 bits of `rs2` to memory |
| `sh`, `sb rs2, off(rs1)` | Write the low 16 bits / low 8 bits of `rs2`; the other bits are ignored |
| `ld`, `sd`, `lwu` | RV64: read and write 64-bit doublewords; read a 32-bit word and zero-extend |

Note the order in the store `sw rs2, off(rs1)`: the datum to be written comes first and the address second. For example, let the starting address of array `A` be in `s3` and the variable `h` in `s2`; the C statement `A[10] = h + A[3];` compiles to

```asm
lw   t0, 12(s3)        # t0 = A[3], address s3 + 3*4
add  t0, s2, t0        # t0 = h + A[3]
sw   t0, 40(s3)        # A[10] = t0, address s3 + 10*4
```

A load must extend short data to the width of the register: C's `signed char` and `short` use `lb` and `lh` for sign extension, and `unsigned char` and `unsigned short` use `lbu` and `lhu` for zero extension. Let the word pointed to by `s0` be `0x00000180` (little-endian, with bytes `80 01 00 00` in order):

```asm
lb   t0, 1(s0)         # t0 = 0x00000001
lb   t1, 0(s0)         # t1 = 0xFFFFFF80: byte 0x80 is sign-extended
lbu  t2, 0(s0)         # t2 = 0x00000080: zero-extended
sb   t1, 2(s0)         # the word at s0 becomes 0x00800180
```

## 3.5. Control Transfer Instructions

### 3.5.1. Conditional Branches

**Assembly language** has no statement blocks, and control flow is implemented by jumping to labels, like `goto` in C. A RISC-V conditional branch compares two registers and branches in one instruction, without relying on condition codes:

| Instruction | Branch condition |
|---|---|
| `beq rs1, rs2, label` | `rs1 == rs2` |
| `bne rs1, rs2, label` | `rs1 != rs2` |
| `blt rs1, rs2, label` | `rs1 < rs2`, signed |
| `bge rs1, rs2, label` | `rs1 >= rs2`, signed |
| `bltu rs1, rs2, label` | `rs1 < rs2`, unsigned |
| `bgeu rs1, rs2, label` | `rs1 >= rs2`, unsigned |

The branch target uses **PC-relative addressing**, with a range of about 4 KiB before and after the current instruction (Section 3.8.3). `bgt`, `ble` and the like are pseudoinstructions obtained by swapping the operands. The benefit of dropping condition codes is that there are no implicit dependences between instructions (in x86 nearly every arithmetic instruction rewrites the flags register), which makes pipelining and out-of-order execution easier to implement.

There is a commonly used trick with unsigned comparison: the bounds check of an array index, `if (i < 0 || i >= n)`, needs only one `bgeu i, n, out_of_bounds`, since a negative `i` is a very large number when viewed as unsigned.

### 3.5.2. Unconditional Jumps

| Instruction | Meaning |
|---|---|
| `jal rd, label` | `rd = pc + 4`, then `pc = label` (PC-relative, range about ±1 MiB) |
| `jalr rd, off(rs1)` | `rd = pc + 4`, then `pc = (rs1 + off) & ~1` |

"And link" means writing the address of the next instruction (the return address) to `rd`, used for function calls: `jal ra, f` calls function `f`, and `jalr zero, 0(ra)` returns at the end of the function. When no return address is needed, setting `rd` to `zero` gives an ordinary jump: `jal zero, label` is the pseudoinstruction `j label`. The target address of `jalr` is given by a register, and it is used for function returns, function pointers, virtual function calls and `switch` jump tables; it clears the lowest bit of the target so that the target is always an even address. `jalr` together with `auipc` can jump anywhere within a 32-bit range (Section 3.6.2).

The range of a branch instruction is limited. To branch farther, the assembler inverts the condition and skips over a `jal`:

```asm
# beq a0, zero, far    (far is out of branch range) becomes
bne  a0, zero, next
j    far
next:
```

### 3.5.3. Compiling Loops and Branches

Turning the control structures of C into branch instructions is the most basic job of a compiler. Take a summation loop as an example; the RV32 code that GCC generates at `-Og` (only optimizations that do not interfere with debugging) and at `-O2`:

```c
int sum_n(int n) {
    int s = 0;
    for (int i = 1; i <= n; i++)
        s += i;
    return s;
}
```

```asm
# gcc -march=rv32im -mabi=ilp32 -Og
sum_n:
    mv   a4, a0            # a4 = n
    li   a5, 1             # i = 1
    li   a0, 0             # s = 0
    j    .L5               # test the condition first
.L6:
    add  a0, a0, a5        # s += i
    addi a5, a5, 1         # i++
.L5:
    ble  a5, a4, .L6       # loop while i <= n
    ret                    # the result is in a0
```

```asm
# gcc -march=rv32im -mabi=ilp32 -O2
sum_n:
    ble  a0, zero, .L6     # n <= 0: the loop body never runs
    addi a4, a0, 1         # a4 = n + 1
    li   a5, 1             # i = 1
    li   a0, 0             # s = 0
.L5:
    add  a0, a0, a5
    addi a5, a5, 1
    bne  a5, a4, .L5       # one branch per iteration
    ret
.L6:
    li   a0, 0
    ret
```

Both versions place the loop condition after the loop body, so only one branch is executed per iteration. `-O2` tests $n \le 0$ once before entering the loop, and inside the loop it uses `bne` to compare with $n + 1$. If the upper bound is changed to the constant 10, `-O2` computes the result directly: the whole function becomes `li a0, 55` and `ret`.

`if-else` is compiled similarly: the condition is inverted, and the `then` part is skipped when it is not satisfied. For example, `return a > b ? a : b;` compiles at `-O2` to

```asm
max:
    mv   a5, a0            # a5 = a
    mv   a0, a1            # assume the result is b
    bge  a1, a5, .L1       # if b >= a, done
    mv   a0, a5            # otherwise the result is a
.L1:
    ret
```

## 3.6. Pseudoinstructions and Large Constants

### 3.6.1. Pseudoinstructions

The code above already contains `mv`, `li`, `j`, `ble` and `ret`, which are not real RISC-V instructions.

**Definition 3.6.1 (Pseudoinstruction)** A mnemonic that the assembly language offers to programmers but that has no corresponding machine instruction, and that the assembler translates into one or several real instructions, is called a **pseudoinstruction**.

Pseudoinstructions make assembly programs more readable without burdening the hardware. The set of real instructions is a subset of the instructions available to the assembly programmer. Common pseudoinstructions (the "Actual instruction" column is the assembler's translation, which can be seen with `objdump -M no-aliases`):

| Pseudoinstruction | Actual instruction | Meaning |
|---|---|---|
| `nop` | `addi x0, x0, 0` | No operation |
| `mv rd, rs` | `addi rd, rs, 0` | Register move |
| `not rd, rs` | `xori rd, rs, -1` | Bitwise complement |
| `neg rd, rs` | `sub rd, x0, rs` | Negation |
| `seqz rd, rs` | `sltiu rd, rs, 1` | `rd = (rs == 0)` |
| `snez rd, rs` | `sltu rd, x0, rs` | `rd = (rs != 0)` |
| `beqz rs, L`, `bnez rs, L` | `beq rs, x0, L`, `bne rs, x0, L` | Compare with zero and branch |
| `bgt rs, rt, L`, `ble rs, rt, L` | `blt rt, rs, L`, `bge rt, rs, L` | Swap the operands |
| `bgtu`, `bleu` | `bltu`, `bgeu` (swapped operands) | Unsigned versions |
| `j L` | `jal x0, L` | Jump |
| `jr rs` | `jalr x0, 0(rs)` | Jump to the address in a register |
| `ret` | `jalr x0, 0(x1)` | Function return |
| `call f` | `auipc x1, %pcrel_hi(f)`<br/>`jalr x1, %pcrel_lo(f)(x1)` | Call a function at any distance |
| `tail f` | `auipc x6, %pcrel_hi(f)`<br/>`jalr x0, %pcrel_lo(f)(x6)` | Tail call, without saving a return address |
| `li rd, imm` | `addi`, or `lui` plus `addi` | Load a constant (Section 3.6.2) |
| `la rd, sym` | `auipc` plus `addi` | Load the address of a symbol |

Pseudoinstructions differ from assembler directives (`.text`, `.word` and so on): a pseudoinstruction eventually produces machine instructions, whereas a directive produces none. At link time the linker can also "relax" instruction sequences that can be shortened into shorter forms, for example replacing the two instructions of a `call` with one `jal` when the target is near enough.

### 3.6.2. Loading Constants and Addresses

The immediate of an I-type instruction has only 12 bits. A 32-bit constant must be split into an upper 20 bits and a lower 12 bits: `lui` loads the upper 20 bits (clearing the lower 12), and `addi` then adds the lower 12 bits:

```asm
lui  a0, 0x87654        # a0 = 0x87654000
addi a0, a0, 0x321      # a0 = 0x87654321
```

One pitfall is that the immediate of `addi` is signed. To get `0xDEADBEEF`, if one writes `lui a0, 0xDEADB` and `addi a0, a0, 0xEEF` directly, the 12-bit immediate `0xEEF` of the latter has its top bit set and is sign-extended to $-273$ (`0xFFFFFEEF`), giving `0xDEADAEEF`. The correct approach is to add 1 to the upper 20 bits:

```asm
lui  a0, 0xDEADC        # a0 = 0xDEADC000
addi a0, a0, -273       # a0 = 0xDEADC000 - 0x111 = 0xDEADBEEF
```

In general, the upper 20 bits of a constant $c$ should be $(c + \mathtt{0x800}) \gg 12$, and the lower 12 bits are $c$ minus that value shifted left by 12 (which lies in $[-2048, 2047]$). The pseudoinstruction `li a0, 0xDEADBEEF` has the assembler do this computation automatically; when the constant is within 12 bits, `li` generates just one `addi`. In RV64 an arbitrary 64-bit constant needs up to 8 instructions, and compilers often read it from memory instead.

The address of a **global variable** is also a constant, but it is not known until link time. In assembly code, `%hi(sym)` and `%lo(sym)` denote the upper 20 bits and the lower 12 bits of the address (including the carry correction above), which the linker fills in. Here is a loop over a global array (GCC `-O2`, RV32I):

```c
int fibo[10];
void fib(void) {
    fibo[0] = 1; fibo[1] = 1;
    for (int i = 2; i < 10; i++)
        fibo[i] = fibo[i - 1] + fibo[i - 2];
}
```

```asm
fib:
    lui  a5, %hi(fibo)
    addi a4, a5, %lo(fibo)  # a4 = &fibo[0]
    li   a3, 1
    addi a5, a5, %lo(fibo)  # a5 = &fibo[0], advanced in the loop
    sw   a3, 0(a4)          # fibo[0] = 1
    sw   a3, 4(a4)          # fibo[1] = 1
    addi a2, a5, 32         # a2 = &fibo[8], end of the loop
    li   a4, 1              # a4 = fibo[1]
    j    .L3
.L5:
    lw   a4, 4(a5)          # a4 = p[1]
    lw   a3, 0(a5)          # a3 = p[0]
.L3:
    add  a4, a4, a3
    sw   a4, 8(a5)          # p[2] = p[1] + p[0]
    addi a5, a5, 4          # p++
    bne  a5, a2, .L5
    ret
```

The compiler does not compute `fibo + 4*i` each time but increments the pointer `a5` by 4 each iteration and rewrites the loop condition as a pointer comparison, saving the multiplication and addition. Position-independent code uses `auipc` instead: `auipc rd, %pcrel_hi(sym)` computes `pc` plus the high offset, and `addi rd, rd, %pcrel_lo(...)` then supplies the low part, which is how `la` is expanded. The global pointer `gp` points to the middle of the static data area, and variables within 2 KiB before and after `gp` can be accessed with a single `lw t0, off(gp)`; the linker performs this relaxation automatically.

## 3.7. Function Calls

### 3.7.1. Steps of a Call

Functions (procedures) are the basic means of structuring programs ([4.1.4](/4.1.4)). At the machine level, a call involves six steps:

1. The caller places the arguments where the callee can get them.
2. Control is transferred to the callee (saving the return address at the same time).
3. The callee acquires the storage it needs (the **stack frame**).
4. The function body is executed.
5. The return value is placed where the caller can get it, and the storage is released.
6. Control is returned to the caller, which continues execution after the call site.

Steps 2 and 6 are done by `jal ra, f` (or `call f`) and `ret`, respectively. How the other steps are done is determined by software convention: if the caller and the callee understand "where the arguments are placed" and "which registers may be used freely" differently, code compiled by different compilers or in different languages cannot call one another.

### 3.7.2. The Calling Convention

**Definition 3.7.1 (Calling Convention)** The set of software rules that specifies how arguments and return values are passed in a function call, which side is responsible for saving each register across the call, and the layout and alignment of the stack, is called the **calling convention**. The calling convention is part of the application binary interface ([4.10.1](/4.10.1#sec-1.3.2)).

The RISC-V calling convention is defined by the RISC-V psABI specification; the main points are:

- Arguments: the first 8 integer (or pointer) arguments are placed in `a0`–`a7` in order; floating-point arguments are placed in `fa0`–`fa7` in ABIs with hardware floating point; further arguments are placed on the stack, with the first stack argument at `0(sp)` at function entry. A scalar of twice the XLEN width (such as `long long` in RV32) is passed in a pair of registers; a structure larger than twice XLEN is handled by **pass by reference** (its address is passed).
- Return values: placed in `a0` (plus `a1` if needed); floating-point return values are placed in `fa0` (`fa1`).
- Stack: it grows toward lower addresses, `sp` points to the top of the stack (the lowest used address), and `sp` must be 16-byte aligned at function entry.
- Responsibility for saving registers:

**Definition 3.7.2 (Caller-Saved and Callee-Saved Registers)** A register that the callee may overwrite freely, and that the caller must itself save before the call if it needs the value after the call, is called a **caller-saved register**; a register that the callee must save before using and restore before returning, and which therefore remains unchanged across the call, is called a **callee-saved register**.

In RISC-V, `ra`, `t0`–`t6`, `a0`–`a7` (and the floating-point registers `ft` and `fa`) are caller-saved; `sp`, `s0`–`s11` (and `fs0`–`fs11`) are callee-saved. That `sp` is callee-saved means that on return `sp` must be restored to its value at the call, or the caller cannot find its own stack frame. Dividing the registers into two classes is a compromise: caller-saved registers suit temporaries that do not live across calls, and callee-saved registers suit variables that must be preserved across calls; the compiler allocates registers accordingly, so that most calls need to save very few registers.

Different data models correspond to different ABI names: `ilp32` (RV32, with `int`, `long` and pointers all 32 bits) and `lp64` (RV64, with `long` and pointers 64 bits); the suffixes `f` and `d` mean that single- or double-precision floating-point arguments are passed in floating-point registers, as in `lp64d`, commonly used on Linux. It is specified at compile time with `-mabi=` and must be compatible with `-march=`.

### 3.7.3. The Stack Frame

The storage a function needs is placed in its **stack frame** ([4.1.4](/4.1.4#sec-4.4); for the memory layout of a program see [4.1.8](/4.1.8#sec-8.3.1)): the callee-saved registers to be saved, the return address `ra` of a non-leaf function, **local variables** that do not fit in registers (arrays, structures, variables whose address is taken), and the extra arguments passed to the next-level function. Allocating and freeing the stack frame is just adjusting `sp`, at the beginning and the end of the function, respectively:

```asm
func:                          # prologue
    addi sp, sp, -16           # allocate a 16-byte frame
    sw   ra, 12(sp)            # save the return address
    sw   s0, 8(sp)             # save callee-saved registers that will be used
    # ... body: may call other functions ...
    lw   s0, 8(sp)             # epilogue: restore registers
    lw   ra, 12(sp)
    addi sp, sp, 16            # free the frame
    ret
```

The code at the beginning is called the prologue, and that at the end the epilogue. A function that calls no other function is called a leaf function; it need not save `ra`, and if it uses only temporary and argument registers it needs no stack frame at all. The frame pointer `s0` (`fp`) is optional: when used it points to the value of `sp` at function entry, local variables can be accessed at fixed offsets relative to `fp`, and a **debugger** can walk back along the frame pointers through the **call stack**; when optimizing, GCC does not use a frame pointer by default and treats `s0` as an ordinary saved register.

The stack before and after the call (addresses decrease downward):

| Address | Content |
|---|---|
| High address | The caller's stack frame |
| | The 9th and later arguments (if any) |
| `sp` at entry → | The callee's stack frame: saved `ra` |
| | Saved `s0`, `s1`, … |
| | Local variables |
| Current `sp` → | Extra arguments for the next level (if any) |
| Low address | Unused |

### 3.7.4. Examples

A leaf function: the arguments are all in registers, and it returns directly after the computation.

```c
int leaf_example(int g, int h, int i, int j) {
    return (g + h) - (i + j);
}
```

```asm
leaf_example:               # g, h, i, j arrive in a0, a1, a2, a3
    add  a0, a0, a1         # a0 = g + h
    add  a2, a2, a3         # a2 = i + j: argument registers are caller-saved
    sub  a0, a0, a2         # the return value goes in a0
    ret
```

A recursive function: `fact` still needs `n` after calling itself, so it puts `n` into the callee-saved register `s0`; since it overwrites `s0` and calls another function, it must save `s0` and `ra` in the stack frame (GCC `-Og`, RV32IM).

```c
int fact(int n) {
    if (n < 1) return 1;
    return n * fact(n - 1);
}
```

```asm
fact:
    ble  a0, zero, .L2      # if n < 1, return 1 without a frame
    addi sp, sp, -16        # frame: 16 bytes, keeps sp 16-byte aligned
    sw   ra, 12(sp)         # save the return address
    sw   s0, 8(sp)          # save the caller's s0
    mv   s0, a0             # s0 = n survives the call
    addi a0, a0, -1         # argument n - 1
    call fact               # a0 = fact(n - 1)
    mul  a0, a0, s0         # a0 = n * fact(n - 1)
    lw   ra, 12(sp)         # restore and return
    lw   s0, 8(sp)
    addi sp, sp, 16
    jr   ra
.L2:
    li   a0, 1
    ret
```

Each level of recursion pushes a 16-byte stack frame, so $n$ levels of recursion use $16n$ bytes of stack; recursion that is too deep causes **stack overflow** ([4.1.10](/4.1.10)). Compiled with `-O2`, GCC rewrites this recursion as a loop, and no stack frame is needed.

## 3.8. Instruction Encoding

### 3.8.1. The Six Formats

The base instructions of RISC-V are all 32 bits. To fit the register fields and immediates required for different purposes into 32 bits, the specification defines six formats:

| Format | 31–25 | 24–20 | 19–15 | 14–12 | 11–7 | 6–0 | Use |
|---|---|---|---|---|---|---|---|
| R | `funct7` | `rs2` | `rs1` | `funct3` | `rd` | `opcode` | Register-register operations |
| I | `imm[11:0]` (12 bits, occupying 31–20) | ← | `rs1` | `funct3` | `rd` | `opcode` | Immediate operations, loads, `jalr` |
| S | `imm[11:5]` | `rs2` | `rs1` | `funct3` | `imm[4:0]` | `opcode` | Stores |
| B | `imm[12,10:5]` | `rs2` | `rs1` | `funct3` | `imm[4:1,11]` | `opcode` | Conditional branches |
| U | `imm[31:12]` (20 bits, occupying 31–12) | ← | ← | ← | `rd` | `opcode` | `lui`, `auipc` |
| J | `imm[20,10:1,11,19:12]` (20 bits, occupying 31–12) | ← | ← | ← | `rd` | `opcode` | `jal` |

(In the table, `imm[12,10:5]` means that these 7 bits are, in order, bit 12 and bits 10–5 of the immediate, written `imm[12|10:5]` in the specification; "←" means that the bit field is merged into the field on its left.)

This set of formats embodies several design decisions:

1. The `opcode` is always in the lowest 7 bits, and `rs1`, `rs2` and `rd` are in the same positions in all formats that use them. The processor can read the register file from fixed bit fields before decoding is finished; values read that are not needed are simply discarded. Reading registers is on the critical path of the processor, which matters for the clock cycle time ([4.10.6](/4.10.6)).
2. The sign bit of the immediate is always bit 31 of the instruction, so sign extension can proceed in parallel with decoding.
3. The bits of the immediate are scrambled in preference to letting the same immediate bit land in different positions in different formats, to reduce the **multiplexers** needed to assemble immediates (Section 3.8.5). The S type splits the immediate into two pieces precisely so as not to move `rs2` and `rd`.
4. The **opcode** fields are grouped by function: `opcode` determines the format and the major class, and `funct3` and `funct7` further distinguish the specific operation, which amounts to a kind of expanded opcode ([4.10.2](/4.10.2#sec-2.2.2)).

### 3.8.2. R-Type and I-Type

The `opcode` of all R-type instructions is `0110011` (OP), and the specific operation is determined by `funct3` and `funct7`. For example `add x8, x9, x10`:

| Field | `funct7` | `rs2` | `rs1` | `funct3` | `rd` | `opcode` |
|---|---|---|---|---|---|---|
| Decimal | 0 | 10 | 9 | 0 | 8 | 51 |
| Binary | `0000000` | `01010` | `01001` | `000` | `01000` | `0110011` |

The machine code is `0000 0000 1010 0100 1000 0100 0011 0011`, that is, `0x00A48433` in hexadecimal. `sub` differs from `add` only in bit 30 of `funct7` (`0100000`), and so do `sra` and `srl`; the hardware can use this bit directly to make the adder subtract or to make the shifter fill with the sign bit. The multiply and divide instructions of the M extension are also R-type, with `funct7 = 0000001`.

The I type merges the `funct7` and `rs2` fields of the R type into a 12-bit immediate, and the other fields are unchanged. For example `addi x15, x1, -50`: the 12-bit two's complement of $-50$ is `111111001110`,

| Field | `imm[11:0]` | `rs1` | `funct3` | `rd` | `opcode` |
|---|---|---|---|---|---|
| Value | $-50$ | 1 | 0 | 15 | `0x13` |
| Binary | `111111001110` | `00001` | `000` | `01111` | `0010011` |

and the machine code is `0xFCE08793`. Load instructions are also I-type (`opcode = 0000011`): in `lw x14, 8(x2)`, `rs1 = 2` is the base register, `rd = 14`, the immediate 8 is the displacement, `funct3 = 010` means word, and the machine code is `0x00812703`. Shift-immediate instructions need only a 5-bit `shamt` (6 bits in RV64), and the upper bits of the immediate serve as a field like `funct7` to distinguish logical from arithmetic right shifts: `srai x5, x6, 3` is `0x40335293`. `jalr` is also I-type (`opcode = 1100111`).

### 3.8.3. S-Type and B-Type

A store instruction needs two source registers (the base `rs1` and the data `rs2`) and a 12-bit displacement, and has no `rd`. To keep `rs2` in the same position as in the R type, the immediate is split in two: the upper 7 bits go in bits 31–25 and the lower 5 bits in the position of the former `rd`. For example `sw x14, 8(x2)`:

| Field | `imm[11:5]` | `rs2` | `rs1` | `funct3` | `imm[4:0]` | `opcode` |
|---|---|---|---|---|---|---|
| Value | 0 | 14 | 2 | 2 (word) | 8 | `0x23` |
| Binary | `0000000` | `01110` | `00010` | `010` | `01000` | `0100011` |

The machine code is `0x00E12423`.

A conditional branch also needs two source registers and an immediate, and its format is the same as the S type; the difference lies in the meaning of the immediate: it is the branch offset in bytes relative to the address of this instruction, and is always even (instructions are 2-byte aligned with the C extension), so the lowest bit need not be stored. The 12-bit immediate field therefore represents a 13-bit offset `imm[12:1]`, with range $[-4096, 4094]$ bytes, that is, about 4 KiB before and after the current instruction:

$$
\text{branch target} = \mathrm{pc} + \operatorname{sext}(\mathrm{imm}[12:1] \,\|\, 0).
$$

The bit arrangement `imm[12,10:5]` and `imm[4:1,11]` of the B-type immediate looks odd; the reason is to align it with the S type as much as possible: `imm[10:5]` and `imm[4:1]` are in the same positions as the corresponding bits in the S type, only the position of the lowest bit in the S type (bit 7) holds `imm[11]` in the B type, and the sign bit `imm[12]` is placed in bit 31. The `opcode` is always `1100011` (BRANCH), and the six branches are distinguished by `funct3` (`beq` is `000`, `bne` is `001`, and `blt`, `bge`, `bltu`, `bgeu` are `100`–`111` in order).

**Example 3.8.1** Encode the first instruction of the following loop:

```asm
Loop: beq  x9, x0, End      # address L
      add  x8, x8, x10      # L + 4
      addi x9, x9, -1       # L + 8
      j    Loop             # L + 12
End:  ...                   # L + 16
```

`End` is 16 greater than the address of `beq`, and the offset $16 = (0\,0000\,0001\,0000)_2$, so `imm[12] = 0`, `imm[10:5] = 000000`, `imm[4:1] = 1000` and `imm[11] = 0`:

| Field | `imm[12,10:5]` | `rs2` | `rs1` | `funct3` | `imm[4:1,11]` | `opcode` |
|---|---|---|---|---|---|---|
| Binary | `0000000` | `00000` | `01001` | `000` | `10000` | `1100011` |

The machine code is `0x00048863`. The final `j Loop` is `jal x0, -12`, encoded as `0xFF5FF06F`.

The benefit of **PC-relative addressing** is that when a whole piece of code moves to another address, the branch encodings in it need not be modified; when only some of the instructions move, only the offsets that cross the moved part need to be recomputed.

### 3.8.4. U-Type and J-Type

The U type has one 20-bit immediate field, placed in the upper 20 bits of the instruction. `lui rd, imm` places it in the upper 20 bits of `rd` and clears the lower 12 bits; `auipc rd, imm` adds the number formed in the same way to the address of this instruction. For example `lui x10, 0xDEADC` is encoded as `0xDEADC537`. Combined with instructions with 12-bit immediates, they can form any 32-bit constant or address (Section 3.6.2).

The J type is used only for `jal`. Its 20-bit immediate field represents a 21-bit even offset `imm[20:1]`, with range $[-2^{20}, 2^{20} - 2]$ bytes, that is, about 1 MiB before and after. Its bit arrangement `imm[20,10:1,11,19:12]` is likewise aligned with the I and U types: `imm[10:1]` at the positions of the corresponding bits in the I type, and `imm[19:12]` at those in the U type. `jalr` is I-type, and its 12-bit immediate is added directly to `rs1`, without an implied 0 in the last bit.

### 3.8.5. Assembling the Immediate

During decoding the processor must assemble a 32-bit sign-extended immediate from the instruction, which is done by a combinational circuit called the immediate generator in the datapath of [4.10.6](/4.10.6). The table below shows which bits of the instruction each part of the 32-bit immediate comes from for each format (filling the upper bits with repeated `inst[31]` is the sign extension):

| Format | Immediate 31–20 | 19–12 | 11 | 10–5 | 4–1 | 0 |
|---|---|---|---|---|---|---|
| I | `inst[31]` | `inst[31]` | `inst[31]` | `inst[30:25]` | `inst[24:21]` | `inst[20]` |
| S | `inst[31]` | `inst[31]` | `inst[31]` | `inst[30:25]` | `inst[11:8]` | `inst[7]` |
| B | `inst[31]` | `inst[31]` | `inst[7]` | `inst[30:25]` | `inst[11:8]` | 0 |
| U | `inst[31:20]` | `inst[19:12]` | 0 | 0 | 0 | 0 |
| J | `inst[31]` | `inst[19:12]` | `inst[20]` | `inst[30:25]` | `inst[24:21]` | 0 |

The effect of the alignment is visible: the sign bit comes from `inst[31]` in all formats; bits 10–5 of the immediate come from `inst[30:25]` in the I, S, B and J types; bits 4–1 have only two sources. Each part of the immediate needs to choose among only two or three sources, so the selectors are small and fast.

### 3.8.6. An Overview of RV32I

RV32I has 40 instructions in all. The table below lists them grouped by `opcode`, with `funct3` and `funct7` in binary:

| `opcode` | Format | Instructions (`funct3`; plus `funct7` where needed) |
|---|---|---|
| `0110111` LUI | U | `lui` |
| `0010111` AUIPC | U | `auipc` |
| `1101111` JAL | J | `jal` |
| `1100111` JALR | I | `jalr` (000) |
| `1100011` BRANCH | B | `beq` (000), `bne` (001), `blt` (100), `bge` (101), `bltu` (110), `bgeu` (111) |
| `0000011` LOAD | I | `lb` (000), `lh` (001), `lw` (010), `lbu` (100), `lhu` (101) |
| `0100011` STORE | S | `sb` (000), `sh` (001), `sw` (010) |
| `0010011` OP-IMM | I | `addi` (000), `slti` (010), `sltiu` (011), `xori` (100), `ori` (110), `andi` (111), `slli` (001; 0000000), `srli` (101; 0000000), `srai` (101; 0100000) |
| `0110011` OP | R | `add` (000; 0000000), `sub` (000; 0100000), `sll` (001), `slt` (010), `sltu` (011), `xor` (100), `srl` (101; 0000000), `sra` (101; 0100000), `or` (110), `and` (111) |
| `0001111` MISC-MEM | I | `fence` (000) |
| `1110011` SYSTEM | I | `ecall` (immediate 0), `ebreak` (immediate 1) |

In the R type, `funct7` is `0000000` where not stated. The eight instructions of the M extension use the `opcode` of OP with `funct7 = 0000001`, and `funct3` is, in order, `mul` (000), `mulh` (001), `mulhsu` (010), `mulhu` (011), `div` (100), `divu` (101), `rem` (110), `remu` (111). The `csrrw` and other instructions of Zicsr also use the `opcode` of SYSTEM. RV64I further has two groups, OP-IMM-32 (`0011011`) and OP-32 (`0111011`), for word operations such as `addiw` and `addw`.

`fence` is used for ordering memory accesses of multiprocessors and device accesses, `ecall` for system calls, and `ebreak` hands control to the **debugger**. A simple implementation can treat `fence` as a no-op and implement `ecall` and `ebreak` as always trapping.

### 3.8.7. Encoding Instructions in Python

By the format table of Section 3.8.1, encoding is just shifting the fields and ORing them together. The functions below implement the six formats and are checked against the examples of the previous sections (the results agree with the output of the GNU assembler):

```python
def bits(x, hi, lo):
    """Return bits hi..lo of x (two's complement for negative x)."""
    return (x >> lo) & ((1 << (hi - lo + 1)) - 1)

def r_type(funct7, rs2, rs1, funct3, rd, opcode):
    return funct7 << 25 | rs2 << 20 | rs1 << 15 | funct3 << 12 | rd << 7 | opcode

def i_type(imm, rs1, funct3, rd, opcode):
    assert -2048 <= imm < 2048
    return bits(imm, 11, 0) << 20 | rs1 << 15 | funct3 << 12 | rd << 7 | opcode

def s_type(imm, rs2, rs1, funct3, opcode):
    assert -2048 <= imm < 2048
    return (bits(imm, 11, 5) << 25 | rs2 << 20 | rs1 << 15 | funct3 << 12
            | bits(imm, 4, 0) << 7 | opcode)

def b_type(imm, rs2, rs1, funct3, opcode=0b1100011):
    assert -4096 <= imm < 4096 and imm % 2 == 0
    return (bits(imm, 12, 12) << 31 | bits(imm, 10, 5) << 25 | rs2 << 20
            | rs1 << 15 | funct3 << 12 | bits(imm, 4, 1) << 8
            | bits(imm, 11, 11) << 7 | opcode)

def u_type(imm20, rd, opcode):
    return bits(imm20, 19, 0) << 12 | rd << 7 | opcode

def j_type(imm, rd, opcode=0b1101111):
    assert -(1 << 20) <= imm < (1 << 20) and imm % 2 == 0
    return (bits(imm, 20, 20) << 31 | bits(imm, 10, 1) << 21
            | bits(imm, 11, 11) << 20 | bits(imm, 19, 12) << 12 | rd << 7 | opcode)

tests = {
    "add x8, x9, x10":   r_type(0b0000000, 10, 9, 0b000, 8, 0b0110011),
    "addi x15, x1, -50": i_type(-50, 1, 0b000, 15, 0b0010011),
    "sw x14, 8(x2)":     s_type(8, 14, 2, 0b010, 0b0100011),
    "beq x9, x0, +16":   b_type(16, 0, 9, 0b000),
    "jal x0, -12":       j_type(-12, 0),
    "lui x10, 0xDEADC":  u_type(0xDEADC, 10, 0b0110111),
}
for asm, word in tests.items():
    print(f"{asm:20s} 0x{word:08x}")
```

### 3.8.8. Compressed Instructions

The C extension provides 16-bit encodings for the most commonly used instructions, such as `c.addi`, `c.lw`, `c.mv` and `c.j`. Their fields are shorter: most can access only the 8 most commonly used registers (`x8`–`x15`, that is, `s0`, `s1`, `a0`–`a5`), the immediates are smaller, and some require the destination register to be the same as a source register. Each compressed instruction corresponds to a 32-bit instruction, so the C extension affects only code density and adds no new functionality, and the processor can first expand it into a 32-bit instruction during decoding.

16-bit and 32-bit instructions can be mixed freely and are distinguished by the lowest two bits: the lowest two bits of a 32-bit instruction are `11`, while those of a compressed instruction are `00`, `01` or `10`. The **decoder** thus knows the length of an instruction from the first two bits, the encoding of instruction lengths forms a **prefix code** ([4.10.2](/4.10.2#sec-2.2.2)), and the specification also reserves encoding space for longer instructions in the future. Of the instructions in a program, 50%–60% can be compressed, reducing code size by about 25%–30%, which matters for instruction caches and for the storage capacity of embedded systems. The cost is that instructions need only be 2-byte aligned, 32-bit instructions may straddle cache lines, and the instruction fetch unit is more complex. This is also why the offsets of branches and `jal` are in units of 2 bytes.

## Summary

- RISC-V is an open, modular RISC instruction set: the base instruction sets RV32I / RV64I plus optional extensions such as M, A, F, D, C and V; the privileged specification defines the three modes M, S and U and the CSRs.
- The register file has 32 general-purpose registers, with `x0` always 0; the ABI names fix the uses of arguments (`a0`–`a7`), the return address (`ra`), the stack pointer (`sp`), temporaries (`t`) and saved registers (`s`).
- Arithmetic instructions operate only between registers, do not detect overflow, and there are no condition codes; the distinction between signed and unsigned appears only in comparison, branches and the extension mode of loads. Multiplication and division come from the M extension, and division by zero raises no exception.
- Memory is byte-addressed and RISC-V is little-endian; loads and stores use **base addressing**, and `lb`/`lbu` and the like determine sign or zero extension. Data should be aligned.
- A conditional branch compares two registers and makes a PC-relative jump (±4 KiB); `jal` (±1 MiB) and `jalr` implement jumps, calls and returns. Pseudoinstructions are translated into real instructions by the assembler; 32-bit constants and addresses are formed with `lui`/`auipc` plus `addi`.
- The calling convention specifies arguments, return values, stack alignment, and the caller-saved (`t`, `a`, `ra`) and callee-saved (`s`, `sp`) registers; functions allocate and free the stack frame with a prologue and an epilogue.
- The six 32-bit instruction formats R, I, S, B, U and J keep the register fields in fixed positions and the sign bit always in bit 31, and the immediate bits are rearranged for this; the 16-bit instructions of the C extension are distinguished by length through the lowest two bits.
