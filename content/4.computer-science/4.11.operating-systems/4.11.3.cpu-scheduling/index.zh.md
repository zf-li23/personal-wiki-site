## 3.1. 工作负载与度量

### 3.1.1. 作业

我们把调度器管理的工作单位称为作业（**进程**或线程）。为了发展最初的几种策略，我们做出一些假设，然后逐个放弃：

1. 每个作业的运行时间相同。
2. 所有作业同时到达。
3. 一旦开始，每个作业都运行到完成。
4. 作业只使用 CPU（没有 I/O）。
5. 每个作业的运行时间是已知的。

最后一个假设最不现实：通用内核并不知道一个进程会运行多久。但它仍然有用，因为假设它的那些策略是最优的，为实用的策略提供了要逼近的标准。

### 3.1.2. 度量

**定义 3.1.1（周转时间与响应时间）** 对于在时刻 $T_{\mathrm{arrival}}$ 到达、在时刻 $T_{\mathrm{first}}$ 首次运行、在时刻 $T_{\mathrm{completion}}$ 完成的作业，**周转时间**为 $T_{\mathrm{turnaround}} = T_{\mathrm{completion}} - T_{\mathrm{arrival}}$，**响应时间**为 $T_{\mathrm{response}} = T_{\mathrm{first}} - T_{\mathrm{arrival}}$。

周转时间衡量批处理用户等待结果的时间；响应时间衡量交互式用户在有所反应之前等待的时间。（在 [4.10.1](/4.10.1) 中，"响应时间"指任务的整个执行时间；在调度中，这个术语有上面这种更窄的含义。）其他准则有**吞吐率**（单位时间内完成的作业数，[4.10.1](/4.10.1)）、公平性（每个作业是否得到它的份额；无限期等待的作业遭受饥饿（starvation））、开销（花在调度器和**上下文切换**上的时间），以及对实时任务而言的满足截止期限。这些准则相互冲突：我们将看到，对周转时间最好的策略，对响应时间很差，反之亦然。

## 3.2. FIFO、SJF 与 STCF

### 3.2.1. 先进先出

**定义 3.2.1（FIFO 调度）** **先进先出**（FIFO，又称先来先服务）调度按作业到达的顺序运行作业，每个作业运行到完成。

FIFO 简单，在作业相似时（假设 1）效果很好。作业不相似时它就失效了。

**例 3.2.1** 作业 A、B、C 依此顺序在时刻 0 到达，运行时间分别为 100、10 和 10。FIFO 在 $[0, 100)$ 运行 A，在 $[100, 110)$ 运行 B，在 $[110, 120)$ 运行 C。周转时间为 100、110 和 120，平均为 110。两个短作业排在长作业后面等待；这就是护航效应（convoy effect），像在超市里排在装满货物的购物车后面一样。

### 3.2.2. 最短作业优先

**定义 3.2.2（SJF 调度）** **最短作业优先**（SJF）调度在每个作业结束时，运行等待中的运行时间最短的作业，并让它运行到完成。

在例 3.2.1 中，SJF 依次运行 B、C、A：周转时间为 10、20、120，平均为 50，而不是 110。

**定理 3.2.1（SJF 的最优性）** 如果所有作业同时到达，并在一个处理器上运行到完成，则 SJF 使平均周转时间最小。

**证明** 设作业按某个顺序运行，运行时间为 $L_1, L_2, \dots, L_n$。第 $k$ 个作业在 $L_1 + \cdots + L_k$ 时完成，所以周转时间之和为

$$
\sum_{k=1}^{n} \sum_{j=1}^{k} L_j = \sum_{j=1}^{n} (n - j + 1)\, L_j .
$$

第 $j$ 个作业的运行时间被计算了 $n - j + 1$ 次：自己一次，它之后的每个作业各一次。如果某个相邻的作业对次序颠倒，即 $L_j > L_{j+1}$，交换这两个作业使和改变 $(n - j + 1) L_{j+1} + (n - j) L_j - (n - j + 1) L_j - (n - j) L_{j+1} = L_{j+1} - L_j < 0$。所以存在"大者在前、小者在后"的次序不可能是最优的，排好序的次序，即 SJF，是最优的。$\square$

### 3.2.3. 最短剩余完成时间优先

当作业在不同的时刻到达时（放弃假设 2），SJF 仍然可能很差。

**例 3.2.2** A（运行时间 100）在时刻 0 到达，B 和 C（运行时间各为 10）在时刻 10 到达。它们到达时，A 已经在运行，非抢占式的 SJF 必须让它运行完：B 和 C 在 110 和 120 完成，平均周转时间为 $(100 + 100 + 110)/3 = 103.3$。

**定义 3.2.3（STCF 调度）** **最短完成时间优先**（STCF，又称最短剩余时间优先，SRTF）是 SJF 的抢占式版本：每当有新作业到达，调度器就比较所有作业（包括正在运行的作业）的剩余运行时间，并运行剩余时间最少的作业。

在例 3.2.2 中，STCF 在时刻 10 抢占 A，在 $[10, 20)$ 运行 B，在 $[20, 30)$ 运行 C，然后运行 A 直到 120。周转时间为 120、10 和 20，平均为 50。当作业在任意时刻到达时，STCF 对平均周转时间是最优的（Schrage 于 1968 年得到的经典结果；证明是与定理 3.2.1 类似的交换论证，应用于一个个工作单元）。

## 3.3. 时间片轮转

### 3.3.1. 响应时间与时间片

对于交互式用户，响应时间很重要。STCF 在这方面表现不佳：在例 3.2.1 中，C 在开始之前要等待 10 个时间单位，作业更多时，最后一个要等待其他所有作业。

**定义 3.3.1（时间片轮转调度）** **时间片轮转调度**（RR）让每个就绪作业最多运行一个时间片（time slice），然后抢占它，把它放到就绪队列的末尾，再运行队首的作业。

**例 3.3.1** A、B、C 在时刻 0 到达，运行时间各为 5。SJF（这里与 FIFO 相同）让它们一个接一个地运行：响应时间为 0、5、10（平均 5），周转时间为 5、10、15（平均 10）。时间片为 1 的 RR 依次运行 A、B、C、A、B、C、……：响应时间为 0、1、2（平均 1），但 A 到 13 才完成，B 到 14，C 到 15，所以平均周转时间为 14，比 SJF 差，接近最坏情形。

这些例子可以用一个小的模拟器验证：

```python
from collections import deque

def simulate(jobs, policy, quantum=1):
    """jobs: list of (name, arrival, length). Returns the schedule as
    (name, start, end) slices and per-job (turnaround, response)."""
    remaining = {n: L for n, a, L in jobs}
    arrival = {n: a for n, a, L in jobs}
    order = {n: i for i, (n, a, L) in enumerate(jobs)}   # tie-break: list order
    t, slices, first, done = 0, [], {}, {}
    queue = deque()                                     # ready queue
    pending = sorted(jobs, key=lambda j: (j[1], order[j[0]]))
    while len(done) < len(jobs):
        while pending and pending[0][1] <= t:           # admit arrivals
            queue.append(pending.pop(0)[0])
        if not queue:                                   # idle until next arrival
            t = pending[0][1]
            continue
        if policy == "FIFO":
            job, run = queue[0], remaining[queue[0]]
        elif policy == "SJF":                           # non-preemptive
            job = min(queue, key=lambda n: (remaining[n], order[n]))
            run = remaining[job]
        elif policy == "STCF":                          # preempt at the next arrival
            job = min(queue, key=lambda n: (remaining[n], order[n]))
            nxt = pending[0][1] - t if pending else remaining[job]
            run = min(remaining[job], nxt)
        elif policy == "RR":
            job, run = queue[0], min(quantum, remaining[queue[0]])
        first.setdefault(job, t)
        queue.remove(job)
        if slices and slices[-1][0] == job and slices[-1][2] == t:
            slices[-1] = (job, slices[-1][1], t + run)  # merge adjacent slices
        else:
            slices.append((job, t, t + run))
        t += run
        remaining[job] -= run
        while pending and pending[0][1] <= t:           # arrivals during the slice
            queue.append(pending.pop(0)[0])
        if remaining[job] == 0:
            done[job] = t
        elif policy == "RR":
            queue.append(job)                           # back of the queue
        else:
            queue.appendleft(job)
    stats = {n: (done[n] - arrival[n], first[n] - arrival[n]) for n, a, L in jobs}
    return slices, stats

def report(title, jobs, policy, **kw):
    slices, stats = simulate(jobs, policy, **kw)
    tat = sum(s[0] for s in stats.values()) / len(stats)
    resp = sum(s[1] for s in stats.values()) / len(stats)
    timeline = " ".join(f"{n}[{a},{b})" for n, a, b in slices)
    print(f"{title:11s} {timeline}")
    print(f"{'':11s} mean turnaround {tat:6.2f}, mean response {resp:6.2f}")

ex1 = [("A", 0, 100), ("B", 0, 10), ("C", 0, 10)]
ex2 = [("A", 0, 100), ("B", 10, 10), ("C", 10, 10)]
ex3 = [("A", 0, 5), ("B", 0, 5), ("C", 0, 5)]
report("FIFO ex1", ex1, "FIFO")
report("SJF ex1", ex1, "SJF")
report("SJF ex2", ex2, "SJF")
report("STCF ex2", ex2, "STCF")
report("SJF ex3", ex3, "SJF")
report("RR(1) ex3", ex3, "RR", quantum=1)
```

            mean turnaround 110.00, mean response  70.00
SJF ex1     B[0,10) C[10,20) A[20,120)
            mean turnaround  50.00, mean response  10.00
SJF ex2     A[0,100) B[100,110) C[110,120)
            mean turnaround 103.33, mean response  63.33

            mean turnaround  50.00, mean response   3.33

这一权衡是根本性的：任何公平的策略，即在短时间间隔内平均分配处理器的策略，都会推迟每个作业的完成；而使周转时间最小的策略则对长作业不公平。

时间片的长度是第二个权衡。时间片越短，响应时间越好，但每次切换都要花时间，既有直接开销，也有缓存变冷带来的开销（[4.11.2](/4.11.2#sec-2.3.3)）。如果一次切换的开销是 $c$，时间片是 $q$，则损失的处理器时间的比例为 $c / (q + c)$：$c = 1\,\mathrm{ms}$、$q = 10\,\mathrm{ms}$ 时约为 9 %，$q = 100\,\mathrm{ms}$ 时约为 1 %。开销被时间片摊销了。实际的内核使用几毫秒的时间片；即使计入缓存效应，切换的开销也远低于 1 %。

### 3.3.2. 计入 I/O

放弃假设 4：启动 I/O 操作的作业会阻塞，调度器应当同时运行另一个作业。如果调度器把两次 I/O 之间的每个 CPU 突发都当作单独的短作业（STCF 就是这样），它自然会偏向交互式作业：每次击键后只计算 1 ms 的文本编辑器立即得到处理器，而长时间的计算则利用中间的空隙。计算与 I/O 的这种重叠，是**多道程序设计**（[4.11.1](/4.11.1#sec-1.2)）最初的理由。

## 3.4. 多级反馈队列

### 3.4.1. 从过去中学习

没有假设 5，调度器就不知道哪些作业是短的。多级反馈队列（MLFQ）最早用于 CTSS（Corbató，1962）以及 BSD Unix、Solaris 和 Windows 的调度器，它从每个作业过去的行为中学习这一点：一直用满整个时间片的作业大概是长的、受 CPU 限制的作业；很快就让出处理器的作业大概是交互式的。

**定义 3.4.1（多级反馈队列）** **多级反馈队列**调度器维护若干个优先级不同的就绪队列，并遵守以下规则：

1. 如果 A 的优先级高于 B，则运行 A（不运行 B）。
2. 如果 A 与 B 的优先级相同，则它们按时间片轮转运行。
3. 进入系统的作业从最高优先级开始。
4. 作业在某个优先级上用完它的时间配额（无论其间让出过多少次处理器）后，优先级降低一级。
5. 经过固定的时间 $S$ 后，把所有作业移到最高优先级（优先级提升）。

规则 3 假定每个新作业都可能是短作业；如果是，它在高优先级上很快完成；如果不是，规则 4 把它降下去，所以 MLFQ 在不知道运行时间的情况下逼近了 SJF。

**例 3.4.1** 三个级别，时间片（等于时间配额）在最高级 Q2 为 10 ms，在 Q1 为 20 ms，在 Q0 为 40 ms。一个长的 CPU 密集型作业 A 在时刻 0 到达：它在 Q2 运行 10 ms，在 Q1 运行 20 ms，从时刻 30 起在 Q0 运行。在时刻 100，一个有 20 ms 工作量的短作业 C 到达。它进入 Q2 并抢占 A（规则 1），用掉 10 ms 的配额后降到 Q1，在那里它的优先级仍高于 A，在时刻 120 完成。C 的周转时间为 20 ms，与 SJF 相同，尽管调度器从不知道它的长度。运行 1 ms 后就等待输入的交互式作业只会缓慢地用掉它的配额，因此留在最高级，得到立即的响应。

### 3.4.2. 为什么需要规则 4 和 5

早期版本的规则让作业只要在时间片到期之前让出处理器，就保持它的优先级。这打开了两个漏洞。作业可以在每个时间片结束前发出一个虚设的 I/O 操作来愚弄调度器，在占用几乎全部处理器的同时停留在最高优先级；规则 4 通过累计每一级上用掉的时间堵住了这个漏洞。而且当许多交互式作业使较高的队列一直很忙时，CPU 密集型作业可能饿死；此外，从 CPU 密集型变为交互式的作业将永远不会再升上去。规则 5 的优先级提升同时解决了这两个问题。它的周期 $S$ 是一个"巫毒常数"：太长则长作业饿死，太短则交互式作业得到的处理器太少。实际的 MLFQ 调度器有许多这样的参数（Solaris 的表有 60 个级别，时间片从 20 毫秒到几百毫秒），有些还允许用户或管理员向调度器提出建议，如 Unix 命令 `nice` 所做的那样。

## 3.5. 比例份额

### 3.5.1. 彩票调度

另一种目标是保证每个作业得到处理器的某个比例，而不是优化周转时间或响应时间。

**定义 3.5.1（彩票调度）** 在**彩票调度**（Waldspurger 与 Weihl，1994）中，每个作业持有若干张彩票。每次调度决策时，调度器均匀随机地抽出一张彩票，并运行持有它的作业；因此在 $T$ 张彩票中持有 $t_i$ 张的作业，在每个时间片中以概率 $t_i / T$ 运行。

随机性使调度器简单且无状态，并且在作业到达或离开时立即适应。它的弱点是短期的不公平：在 $n$ 个时间片中，份额为 $p = t_i/T$ 的作业赢得的次数服从**二项分布** $\mathrm{Bin}(n, p)$，其相对标准差 $\sqrt{(1 - p)/(np)}$ 只按 $1/\sqrt{n}$ 的速度减小。各有 100 个时间片的两个相同作业，完成时间平均而言有明显的差距；比例只有在长期才是精确的（由**大数定律**）。

### 3.5.2. 步长调度

**定义 3.5.2（步长调度）** 在**步长调度**中，每个作业 $i$ 有一个步长 $s_i = K / t_i$，与它的彩票数 $t_i$ 成反比（$K$ 是一个很大的常数），还有一个初值为 0 的行程值（pass）。调度器总是运行行程值最小的作业，并在它用完时间片之后，把它的行程值增加一个步长。

**例 3.5.1** 作业 A、B、C 分别持有 100、50 和 250 张彩票；取 $K = 10000$，步长为 100、200 和 40。平局时按字母顺序：

| A 的行程值 | B 的行程值 | C 的行程值 | 运行 |
|---|---|---|---|
| 0 | 0 | 0 | A |
| 100 | 0 | 0 | B |
| 100 | 200 | 0 | C |
| 100 | 200 | 40 | C |
| 100 | 200 | 80 | C |
| 100 | 200 | 120 | A |
| 200 | 200 | 120 | C |
| 200 | 200 | 160 | C |
| 200 | 200 | 200 | A |

经过 8 个时间片，所有行程值再次相等（200）：C 运行了 5 次，A 两次，B 一次，恰好是比例 $250 : 100 : 50$。步长调度是确定性的，并且在每个这样的周期上是精确的。它的缺点是有全局状态：后到达的作业必须被赋予一个合理的行程值（如果从 0 开始，它就会独占处理器），而彩票调度不需要这样的小心。

### 3.5.3. 完全公平调度器

比例份额的思想，以步长调度的确定性形式，是 Linux 调度普通进程的基础。完全公平调度器（Completely Fair Scheduler），简称 CFS由 Ingo Molnár 编写，从 2.6.23 版（2007 年）到 6.5 版一直是 Linux 的调度器。

CFS 为每个任务保存它的虚拟运行时间（virtual runtime）`vruntime`，即它已经运行的时间按权重缩放后的值，并总是运行虚拟运行时间最小的任务：到目前为止得到的公平份额最少的任务。任务按虚拟运行时间排序，保存在一棵**红黑树**中，所以下一个任务（最左的结点）借助缓存的指针可在 $O(1)$ 时间内找到，把任务插回去则需 $O(\log n)$。权重来自**进程**的 nice 值（nice value），它是从 $-20$（最高优先级）到 $19$（最低优先级）的整数，默认为 0：

$$
w(\mathit{nice}) \approx \frac{1024}{1.25^{\mathit{nice}}}, \qquad
\Delta\mathit{vruntime} = \Delta t \cdot \frac{1024}{w} .
$$

内核使用固定的表（`sched_prio_to_weight`）：nice $-20$：88761，$-5$：3121，$-1$：1277，0：1024，1：820，5：335，10：110，19：15。每一个 nice 步长使权重改变约 1.25 倍，因此相对于竞争者，一个进程会多得或少得约 10 % 的处理器；份额只取决于权重之比。nice 为 0 的进程与 nice 为 5 的进程竞争时，应得到一个 CPU 的 $1024 / (1024 + 335) = 75.3\,\%$。把两个 CPU 密集型循环固定在同一个 CPU 上运行 3 秒的测量证实了这一点：

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

/* Count loop iterations for a fixed wall-clock time. */
int main(int argc, char **argv) {
    double seconds = argc > 1 ? atof(argv[1]) : 3.0;
    struct timespec t0, t;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    unsigned long n = 0;
    do {
        for (int i = 0; i < 100000; i++) __asm__ volatile ("");
        n++;
        clock_gettime(CLOCK_MONOTONIC, &t);
    } while ((t.tv_sec - t0.tv_sec) + (t.tv_nsec - t0.tv_nsec) * 1e-9 < seconds);
    printf("%s %lu\n", argc > 2 ? argv[2] : "", n);
    return 0;
}
```

```bash
taskset -c 3 ./spin 3 "nice 0:" & taskset -c 3 nice -n 5 ./spin 3 "nice 5:" & wait
```

```text
nice 0: 111282
nice 5: 37380
```

第一个进程完成了 $111282 / (111282 + 37380) = 74.9\,\%$ 的工作。CFS 还有两个要素。它力求在一个目标延迟（`sched_latency`，默认 6 ms，随 CPU 数目缩放）内让每个可运行任务都运行一次，给每个任务与其权重成比例、但不少于最小粒度的时间片。而且睡眠后被唤醒的任务被放在当前最小虚拟运行时间附近，而不是它原来较小的值，这样长时间睡眠的任务在被唤醒后就不能独占处理器。

### 3.5.4. EEVDF

CFS 公平地划分处理器，但没有延迟的概念：需要快速但短暂地得到处理器的任务（音频线程、交互式程序）无法提出这一要求而不同时要求更大的份额，而偏向被唤醒任务的启发式规则又很脆弱。自 Linux 6.6（2023 年 10 月）起，公平调度类使用最早合格虚拟截止期限优先（EEVDF）算法，它由 Stoica 与 Abdel-Wahab 于 1995 年发表，由 Peter Zijlstra 在 Linux 中实现。它保留 CFS 的权重和虚拟运行时间，并增加两个概念：

**定义 3.5.3（EEVDF 调度）** 设任务 $i$ 的权重为 $w_i$、虚拟运行时间为 $v_i$，并设 $V = \sum_i w_i v_i / \sum_i w_i$ 为可运行任务虚拟运行时间的加权平均。任务 $i$ 的滞后（lag）为 $\ell_i = w_i (V - v_i)$，即它应得（$\ell_i > 0$）或已多得（$\ell_i < 0$）的服务量；若 $\ell_i \ge 0$，则称任务是合格的（eligible）。每个任务请求一个时间片 $r_i$，它的虚拟截止期限为 $d_i = v_i + r_i / w_i$。**最早合格虚拟截止期限优先**（EEVDF）调度总是在合格的任务中，运行虚拟截止期限最早的那个。

合格性保持公平（没有任务比它的份额多跑出一个时间片以上），截止期限表达延迟：请求短时间片的任务截止期限早，所以运行得早、但运行的时间短，而它的长期份额仍然只由权重决定。

**例 3.5.2** 任务 A 和 B 的权重同为 1；A 请求 3 ms 的时间片，B 请求 1 ms。两者起初都有 $v = 0$。表中 $V$ 是虚拟运行时间的平均值，$d$ 是每次决策时的虚拟截止期限：

| 时间 | $V$ | $v_A$ | $v_B$ | 合格 | $d_A$ | $d_B$ | 运行 |
|---|---|---|---|---|---|---|---|
| 0 | 0 | 0 | 0 | A、B | 3 | 1 | B |
| 1 | 1/2 | 0 | 1 | A | 3 | 2 | A |
| 4 | 2 | 3 | 1 | B | 6 | 2 | B |
| 5 | 5/2 | 3 | 2 | B | 6 | 3 | B |
| 6 | 3 | 3 | 3 | A、B | 6 | 4 | B |
| 7 | 7/2 | 3 | 4 | A | 6 | 5 | A |
| 10 | 5 | 6 | 4 | B | 9 | 5 | B |
| 11 | 11/2 | 6 | 5 | B | 9 | 6 | B |

在最初的 12 ms 内，每个任务得到 6 ms，正如它们相等的权重所要求的；但 B 从不等待超过 3 ms，而要求长时间片的 A 则一次得到完整的时间片。

在 Linux 中，默认请求的时间片是基本时间片（base slice，`/sys/kernel/debug/sched/base_slice_ns`，在有 8 个或更多 CPU 的机器上约为 3 ms）；自 Linux 6.12 起，任务可以通过 `sched_setattr` 系统调用请求不同的值。睡眠任务的滞后被记住并逐渐衰减，所以任务不能靠睡眠获得服务，也不会因短暂阻塞而失去服务。实际的实现把可运行任务保存在一棵增强的红黑树中，能在 $O(\log n)$ 时间内找到截止期限最早的合格任务。

### 3.5.5. Linux 实际使用的调度类

Linux 按严格的优先级顺序运行几个调度类（scheduling class）；任务的类由它的调度策略决定：

| 类 | 策略 | 行为 |
|---|---|---|
| 截止期限 | `SCHED_DEADLINE` | 带预留（运行时间、周期、截止期限）的最早截止期限优先；用于周期性实时任务 |
| 实时 | `SCHED_FIFO`、`SCHED_RR` | 固定优先级 1–99；FIFO 一直运行到阻塞或让出，RR 在相同优先级之间增加时间片 |
| 公平 | `SCHED_NORMAL`（也称 `SCHED_OTHER`）、`SCHED_BATCH`、`SCHED_IDLE` | 带 nice 权重的 EEVDF；BATCH 从不被当作交互式；IDLE 只得到其他方面空闲的时间 |
| 可扩展 | `SCHED_EXT` | 以 eBPF 程序提供的调度策略（sched_ext，自 Linux 6.12 起） |

永不阻塞的实时任务会饿死其他一切；默认情况下，内核为非实时任务保留每秒的 5 %（`/proc/sys/kernel/sched_rt_runtime_us` = 950000，`sched_rt_period_us` = 1000000）。sched_ext 使新的策略可以在运行时加载而无需重新构建内核，用于实验以及游戏和大型服务器等负载；如果 eBPF 调度器行为失常，内核退回到公平类。

日常使用的命令：

```bash
nice -n 10 ./long_analysis.sh      # start with lower priority (nice 10)
renice -n 5 -p 12345               # change the nice value of a running process
chrt -p 12345                      # show the policy and priority of a process
ps -o pid,ni,cls,pri,comm -p 12345 # nice value and class in ps
```

普通用户只能增大自己进程的 nice 值；减小它，或选择实时策略，需要特权。在共享服务器上，用 `nice -n 19` 运行长时间的计算，是对其他用户的体谅。

## 3.6. 多处理器调度

### 3.6.1. 缓存与亲和性

有多个处理器时，调度器还必须决定每个作业在哪里运行。一直在某个 CPU 上运行的作业已经预热了该 CPU 的缓存（以及它的快表，[4.11.4](/4.11.4)）；换到另一个 CPU，它必须重新加载一切。因此调度器倾向于缓存亲和性（cache affinity）：让作业留在它以前运行的 CPU 上，除非各 CPU 之间的不平衡变得太大。

有两种基本的设计：

- 单队列多处理器调度（SQMS）维护一个共享的就绪队列，每个 CPU 都从中取作业。它自动平衡负载，但共享的队列需要锁，在 CPU 很多时成为瓶颈，而且作业在 CPU 之间随意迁移，失去亲和性。
- 多队列多处理器调度（MQMS）给每个 CPU 一个自己的队列，独立调度。它有良好的可扩展性并保持亲和性，但队列可能变得不平衡：一个 CPU 空闲，而另一个有三个作业。补救办法是迁移，通常通过工作窃取（work stealing）：负载较轻的 CPU 查看其他 CPU 的队列，从较忙的队列中取走作业。

Linux 使用每个 CPU 一个的运行队列，并在反映硬件结构的调度域层次内，周期性地并在某个 CPU 空闲时对它们做均衡：同一个核的超线程共享缓存，所以在它们之间移动任务的代价小；同一个插槽的各核共享最后一级缓存；在插槽之间（各有自己内存的 NUMA 结点）移动代价最大，也最不情愿进行。在拥有不同类型核的处理器（如较新的 Intel 和 ARM 设计中的性能核与能效核）上，调度器还会借助硬件的提示，考虑核的能力。

### 3.6.2. 实际后果

- 程序可以用 `taskset` 或 `sched_setaffinity` 限制自己运行的 CPU（在 [4.11.2](/4.11.2#sec-2.3.3) 和 3.5.3 节的测量中用到了）；批处理系统和容器通过控制组限制它们（[4.11.9](/4.11.9)）。
- 并行程序启动的 CPU 密集型线程或进程，不应多于它们可用的 CPU 数。超额订阅（oversubscription），例如由 8 个工作进程组成的**进程池**、每个工作进程运行一个有 8 个线程的多线程 **BLAS**（[4.4.7](/4.4.7)），会引起持续的上下文切换和缓存抖动，通常比大小合适的进程池运行得更慢。
- 紧密合作的线程（共享数据、相互等待）如果不是同时被调度，就会吃亏；成组调度（gang scheduling），又称协同调度让它们一起运行，这对集群上的并行作业很重要（[4.11.11](/4.11.11)）。
- 进程可以使用的 CPU 数由 `nproc` 报告，它尊重亲和性掩码；Python 中的 `os.cpu_count()` 报告机器的全部 CPU，而 `os.process_cpu_count()`（Python 3.13）报告进程可用的 CPU。

## 小结

- 周转时间（完成减到达）和响应时间（首次运行减到达）是主要的度量；公平性、吞吐率和开销是另外的度量。有利于其一的策略不利于另一个。
- FIFO 受护航效应之苦。当所有作业一起到达时，SJF 对平均周转时间是最优的（交换论证），一般情形下 STCF 是最优的；两者都需要运行时间，并饿死长作业。
- 时间片轮转响应时间好而周转时间差；时间片在响应能力与上下文切换的摊销开销之间折中。
- MLFQ 学习哪些作业是交互式的：新作业从最高优先级开始，用完配额的作业下移，周期性的提升防止饥饿和被愚弄。
- 比例份额给每个作业处理器的一个比例：彩票调度是随机的，步长调度是确定的。CFS（2007–2023）运行加权虚拟运行时间最小的任务；EEVDF（Linux 6.6 及以后）运行虚拟截止期限最早的合格任务，在公平之外增加了对延迟的控制。nice 值设置权重，每一步约 10 %。
- 在多处理器上，每个 CPU 一个队列并带负载均衡，可以保持缓存亲和性；避免超额订阅 CPU，并使用 `taskset`、`nice` 以及批处理系统的 CPU 限制。
